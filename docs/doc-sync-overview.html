How the Doc Sync agent works

Doc Sync is the heart of the pipeline. It drives four documentation authors over one story — in strict order, with a human approval after each — and leaves a four-file bundle on disk for the Build stage to commit. Here is exactly what it invokes, what every other stage does around it, and where each artifact lands.

/run-pipeline→ conductor→ intake-agent→ doc-sync-agent→ build → review → verify → release → publish

05 · The shared toolbox

Skills, rules, hooks & the entry command

Skills · .claude/skills/

  • story-fetcher — read a story from Jira / Confluence / Word (Atlassian MCP, read-only). Intake only.
  • workspace-writer — write a file in the repo, never .env, never outside root. Nearly every stage.
  • branch-committer — branch, stage, commit, push (GitHub MCP). Never base branch, never merge. Build · Verify · Release.
  • pull-request-opener — open the PR with 5 sections (GitHub MCP). Release.
  • review-poster — post approved findings as PR comments. Release.
  • page-publisher — create/update the one Confluence page. Publish.
  • evidence-logger — record the test counts a human reports. Verify.

Guardrails · .claude/rules/guardrails.md

  • G1 Jira stays read-only — Intake only.
  • G2 GitHub writes via named skills; feature branch only; no agent merges.
  • G3 Confluence — one summary page, one space, Publish only.
  • G4 Everything traces to a real source; gaps are [pending]; closed data model.
  • G5 Secrets stay out; .env never read, written, or committed.
  • G6 Checkpoints are real stops; nothing leaves the repo unseen.
  • G7 Stay in your lane — each stage edits only the files it owns.

Lifecycle hooks · .claude/hooks/

Prose instructions the agent performs as steps — there is no background runner, nothing in settings.json fires them.

  • before-work — re-read inputs, confirm app-profile.yml fields are filled, check every named input file exists; halt and ask if one is missing.
  • after-work — append a row to trace-log.md and overwrite handoff.md, in a single write. Fires once per top-level agent (Doc Sync collects its four author rows first).

Command & external systems

/run-pipeline [EPMCDMETST-<n>] — the one entry point; launches the conductor. Blank arg → browse the backlog.

  • Atlassian MCP — Jira (read) + Confluence (write). Used by Intake & Publish.
  • GitHub MCP — branches, commits, PRs, comments. Used by Build, Verify & Release.
  • The MCP servers hold their own credentials — agent logic never handles tokens.
06 · Easy to miss

Details worth pinning down

Sub-agents aren't launchable Agent types

The four authors are path-referenced files Doc Sync reads and follows — they don't appear to the Agent tool. Only the eight files in .claude/agents/ launch directly.

The first commit is the whole doc bundle

Authors leave all four files uncommitted. The Build agent cuts the branch and makes the docs the very first commit, bundled with the code — never a PR at that point.

Only three stages are skippable

Architecture, Design Review and Implementation Planning can be skipped with explicit consent, logged. Intake, Requirements, Build and Verify cannot.

trace-log appends, handoff overwrites

trace-log.md is the growing audit trail; handoff.md is replaced each stage so it always shows "where we are now" — paste it into a fresh session to resume after a crash.

app-profile.yml must be filled first

The conductor checks the essentials (app.name, tech, data_model.entities, local_run.start, github.repo) before Intake runs, and asks rather than guessing.

MCP servers are a hard dependency

Intake/Publish need the Atlassian MCP; Build/Verify/Release need the GitHub MCP. If a server isn't registered, that stage stops and asks — it never fabricates a result.

Current repo state: the Atlassian and GitHub MCP servers are not yet registered (claude mcp list → none). A live /run-pipeline will reach Doc Sync (all local work) but stall at the first external call until they're wired.
